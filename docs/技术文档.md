# DC Modpack Creator 技术文档

项目使用uv管理依赖

## 1. 目标

Windows 图形化 Minecraft 客户端整合包导出工具，使用 Python + PySide6。从工作目录的“导出”文件夹读取多份 TOML，一次选择、一键开始，分别收集文件、构造目录并导出。

- 每份配置可以对应不同游戏实例，也可以为同一实例设置不同导出内容。
- 支持原版、Fabric、Forge、NeoForge，自动识别 MC 和加载器版本。
- 所有选中文件内嵌打包进zip，不查询资源平台、不生成资源下载引用。安装游戏时仅联网获取 Java、游戏本体和依赖（这个依赖PCL/modrinth pack的自动安装功能，无需自行实现）。
- 每份配置选择一种产物：mrpack包，或包含本地 PCL 启动器与个性化内容的完整 ZIP。
- 支持批量任务串行导出、独立进度、失败隔离、单任务多线程压缩，以及完整包的原生 ZIP 分卷。
- 开始导出前统一询问是否替换同名旧文件，全部确认后才执行；各任务准备完成、最终压缩前删除旧文件，直接在目标目录输出压缩包。

不需要实现 GUI 内完整编辑配置功能。

## 2. 工作目录与配置

### 2.1 路径约定

工作目录取程序启动时的当前目录，由终端或快捷方式的“起始位置”决定。工具自身的安装目录只用来定位随程序携带的资源和压缩引擎。

- 每份导出配置可在 `[source]` 中设置 `base_dir`，省略时默认为 `"."`。其相对路径以程序启动时的工作目录为基准（不是 TOML 所在目录），也允许绝对路径。
- 导出配置中的 `source.instance_dir`、`launcher.executable`、`extras.source` 和显式设置的 `output.directory`，相对路径均以该配置的 `base_dir` 为基准，也允许绝对路径。
- 输出目录由每份导出配置的 `output.directory` 控制，省略时默认为 `base_dir` 下的“导出”目录。工具设置不提供输出目录；自定义临时目录仍以工作目录为基准，也允许绝对路径。
- 应用数据目录固定为工作目录下的“导出/dc-modpack-creator”，配置为其中的 config.toml，日志写入 logs/；更改整合包最终导出位置不改变应用数据目录。
- 游戏文件选择规则相对 source.instance_dir。
- extras.destination 相对包内附加根：完整包是外层 ZIP 根，mrpack包是 mrpack 根。
- 启动后台进程前先解析为绝对路径，后台进程自己的当前目录不影响配置含义。

### 2.2 工具配置和导出配置

```text
工作目录/
└─ 导出/                          # 任务配置与默认成品输出位置
   ├─ dc-modpack-creator/          # 应用自身的数据目录
   │  ├─ config.toml              # 工具设置与状态，不是导出任务
   │  └─ logs/                    # 日志
   ├─ DC生存服.toml               # 导出任务
   ├─ DC活动服.toml               # 导出任务
   └─ 整合包名-版本.zip           # 导出成品；.mrpack 与分卷也放在此处
```

- 扫描“导出”第一层的 .toml以读取导出配置，按文件名排序
- 工具配置保存全局设置、上次勾选和窗口状态
- 工具配置与导出配置的压缩参数统一放在 `[output]`：`compression_level` 为压缩等级，`compression_volume_size` 为容量字符串（如 `"400MB"`、`"4GB"`，`"0"` 关闭分卷）。导出配置省略字段时继承工具设置；mrpack 不继承全局分卷大小，且不允许显式启用分卷。`output.directory` 仅由导出配置控制。
- 应用数据目录及日志目录不存在时创建，工具配置不存在时生成默认文件。

## 3. 导出产物

### 3.1 mrpack包

```text
整合包名-版本.mrpack               # 单文件 ZIP 容器
├─ modrinth.index.json
├─ overrides/                     # 安装到游戏目录的文件
│  ├─ mods/...
│  ├─ config/...
│  └─ ...
└─ 额外文件或目录                  # 供用户另行取用
```

按 [Modrinth 格式](https://support.modrinth.com/en/articles/8802351-modrinth-modpack-format-mrpack)生成 UTF-8 的 modrinth.index.json，填写包名、包版本、可选简介及 MC / 加载器依赖。选中的游戏文件全部放入 overrides，下载清单 files 为空。

mrpack包始终为单个 .mrpack，不自动复制 PCL 配置和PCL启动器程序。额外文件放在mrpack根目录（不过安装时不会自动安装到游戏目录）

### 3.2 完整包

```text
整合包名-版本.zip
├─ 启动Minecraft.exe             # 复制本地指定的 PCL EXE，固定使用此名称
├─ modpack.mrpack                 # 固定名称
├─ PCL/                          # 启动器个性化内容
└─ 额外文件或目录
```

玩家解压后运行启动器，安装内嵌 mrpack；游戏依赖由启动器自行联网补齐。工具只复制本地指定的启动器，无论源 EXE 名称是什么，包内都固定命名为“启动Minecraft.exe”；缺失时报错，不下载替代品。

### 3.3 分卷压缩

```text
整合包名-版本.z01
整合包名-版本.z02
...
整合包名-版本.zip                # 最后一卷，包含 ZIP 目录
```

- 分卷压缩只对完整包启用，打mrpack包时不支持分卷
- 不足一卷时输出正常的单个 .zip
- 配置中分卷大小为非负整数字节，0 关闭。

## 4. 文件选择与目录构造

### 4.1 实例元数据

实例按开启版本隔离的目录布局处理：instance_dir 内包含同名版本 JSON，以及 mods、config 等游戏文件。从同名版本 JSON 读取实例信息，解析 MC 和加载器版本。支持 PCL 自包含实例的 `clientVersion`；自定义实例名不覆盖该字段。禁止从实例名称猜测版本。

支持依赖 ID 为 minecraft、fabric-loader、forge、neoforge。版本无法确定或遇到未支持加载器时，该任务预检失败。

包名和包版本由配置填写，包版本与 MC 版本分别处理。

### 4.2 游戏文件规则

逐个枚举 instance_dir 内的游戏文件，以其相对 instance_dir 的路径匹配规则，生成最终文件清单和命中统计。路径模式采用 [Git 官方 gitignore 文档](https://git-scm.com/docs/gitignore#_pattern_format)定义的语法，通过 pathspec 的 GitIgnoreBasicPattern 实现

具体按以下规则执行：

1. 初始所有文件不选中，从上到下处理，后命中覆盖先命中。
2. 普通行包含文件，! 开头的行排除文件；空行、以 # 开头的注释行忽略。保留行首空格；行尾空格忽略，除非用反斜杠转义。
3. 规则中只能用 / 分隔目录，待匹配的 Windows 文件路径统一转换为 /，匹配不区分大小写。
4. 开头或中间含 / 的模式相对 instance_dir 根匹配；开头 / 表示根锚定，不是操作系统绝对路径。没有开头或中间 / 的模式在任意层级匹配文件或目录名，例如 *.log 匹配任意层级日志，/latest.log 仅匹配根目录。末尾 / 只匹配目录，并选择其全部后代；不带末尾 / 的模式也可以命中同名目录。单独 / 按 Git 行为忽略。
5. `*`匹配单个路径段内零个或多个字符，`?` 匹配单个非 / 字符；`[abc]、[!abc]、[a-z]` 匹配单个字符，字面量 ] 可直接使用。`**/foo` 匹配任意层级的 foo，`a/**/b` 匹配 `a/b`、`a/x/b`、`a/x/y/b`，`abc/**` 匹配 abc 下全部后代。
6. 不执行变量、环境变量或命令替换；中文、空格和 $ 作为普通路径字符处理。
7. 输出及临时目录与输入目录的交叉关系在预检中检查，防止递归收集成品。

### 4.3 额外文件

- 按 extras 映射复制文件或递归目录；保留目录内部层级
- mrpack包放 mrpack 根，完整包放外层 ZIP 根。源不存在或不可读时本任务失败。
- 目标必须为合法的包内相对路径，不允许盘符、绝对路径、空目标或 . / .. 路径段。

### 4.4 完整包的 PCL 内容

仅完整包自动执行以下复制：

| 来源                                                           | 目标                         |
| -------------------------------------------------------------- | ---------------------------- |
| source.instance_dir/PCL                                        | 内嵌 mrpack 的 overrides/PCL |
| launcher.executable                                            | 外层 启动Minecraft.exe       |
| 启动器个性化源下的 Pictures、Musics、Help                      | 外层 PCL 下的同名目录        |
| 启动器个性化源下的 Custom.xaml、Setup.ini、hints.txt、Logo.png | 外层 PCL 下的同名文件        |

个性化源使用本地启动器 EXE 同目录下的 PCL

## 5. 批量执行与界面

### 5.1 界面功能

UI 样式和具体布局见 [UI 设计](UI设计.md)

### 5.2 任务流程与调度

```text
整批预检 → 确认所有同名文件的替换 → 按序执行任务
单项任务： 收集并复制文件 → 生成 mrpack →  删除已确认的旧文件
                          → 压缩完整 ZIP（完整包）→ 成功
```

- 同目录同基础名的两个完整包任务互相冲突，包括分片参数不同的情况；两个mrpack包写同一 .mrpack 也冲突。冲突任务均预检失败
- 每份任务独立预检和处理错误，一份失败不打断其他任务。
- 整批预检完成后，对可执行任务的已有目标文件统一弹窗确认替换；所有替换均确认后才开始队列。
- 导出任务固定串行执行，当前任务成功、失败或取消并完成后台作业停止及临时产物清理后，才启动下一项
- 压缩线程数只在工具设置中配置，控制当前任务的单个 7za 压缩进程；0 自动取逻辑处理器数量，正数指定压缩工作线程上限
- 扫描时使用不定进度，复制按已处理字节更新，压缩按对应阶段的实际进度更新展示
- 取消排队任务时直接标记已取消，不启动该任务；取消当前任务时，先停止相关后台作业并清理临时产物，再继续队列
- 重试时重新读取配置和全局设置，作为新任务执行，不从旧压缩中间状态续传。

## 6. 压缩与原生分卷实现

### 6.1 ZIP 压缩

随工具携带独立 7za.exe，调用此工具执行压缩操作。所有归档显式指定 ZIP 格式，包括 .mrpack，自动启用 ZIP64。

固定使用官方 7-Zip Extra 25.01 Windows x64；来源、源码链接、归档及可执行文件 SHA-256 和许可见 [引擎说明](../src/dc_modpack_creator/vendor/README.md)。执行前验证随附引擎摘要。QProcess 使用参数数组与 UTF-8 清单，不通过 shell 展开文件名。

- 压缩等级允许 0、1、3、5、7、9，默认 5：0 为 Store 档，仅存储；其他档使用 Deflate。
- mrpack 按所选等级压缩；外层完整 ZIP 中的 modpack.mrpack 使用 Store，其他条目遵循所选压缩等级。
- 引擎可能对压缩后反而增大的小文件自动使用 Store，这是 7-Zip 自身的优化。
- 外层 ZIP 先写其他内容，再以 Store 添加内层 mrpack。7-Zip 更新归档时的临时文件通过 `-w` 限定在本任务的临时目录中，一并清理。

### 6.2 ZIP 原生分卷

随附 Info-ZIP Zip 3.0 Windows x64 `zip.exe`，与 7za 一样在任务写入或删除文件前校验固定 SHA-256。来源、许可、原始发行包及可执行文件摘要见 [引擎说明](../src/dc_modpack_creator/vendor/README.md)。只有启用分卷的完整包需要此工具。

1. 在输出目录下创建独立 `.dc-zip-*` 临时目录；7za 在其中生成 `complete.zip`，先压缩外层内容，再以 Store 添加 `modpack.mrpack`。
2. 若归档大小不超过实际分卷上限，直接发布普通单个 `.zip`。
3. 否则通过 QProcess 调用 `zip.exe -s <整KB大小>k complete.zip --out split.zip`，复制归档条目生成 `split.z01 … split.zip`，保留压缩方法、CRC 和压缩数据。命令行使用临时目录中的 ASCII 相对文件名，输出基础名由 Python 在发布时恢复，避免旧版工具的命令行路径编码限制；包内 Unicode 名称保留。子进程移除 `ZIP`、`ZIPOPT` 环境变量，避免额外选项影响导出。
4. 进度根据临时分卷已写字节估算；Info-ZIP 写入时可能重命名当前卷，进度采样容忍这一变化。进程必须正常退出且退出码为 0，才发布文件组。发布使用 Windows 不覆盖现有文件的重命名，并逐个记录本任务拥有的文件。
5. 取消或失败时先终止进程并等待退出，再清理已发布文件及两个临时目录；发布期间新出现的同名外部文件不会被覆盖或删除。成功后清理临时完整 ZIP，只保留最终文件组。

本工具只使用「完整 ZIP → 原生分卷」方向。验证中发现此旧版 Info-ZIP 的反向 `-s 0` 合并对跨卷 ZIP64 条目可能截断数据

### 6.3 后台运行

GUI 使用 PySide6。文件扫描、复制、元数据处理和旧文件删除放入后台工作线程；压缩通过 QProcess 启动，以信号更新界面。

- 读取进度流时处理回车刷新和普通换行；进程退出后再判断阶段是否完成。
- 所有压缩与分卷进程退出码为 0，且必要的发布及清理完成后标记成功，不增加产品运行时的成品校验环节；非零退出按失败记录，包括可能遗漏文件的压缩警告。用户主动停止单独显示“已取消”。

## 7. 预检、覆盖与清理

### 7.1 预检

- 检查配置可读性、规则、版本信息、源文件、目标冲突、输出权限及估算空间
- 对整批所有递归输入目录检查交叉影响，包括 instance_dir、extras 目录和启动器个性化目录。任何任务的输出和临时目录均不得位于这些输入目录内部。

### 7.2 覆盖确认与直接输出

1. 预检时列出每个任务已存在的目标文件。mrpack包检查同名 .mrpack；完整包检查同基础名的 .zip、.z01、.z02 等原生分卷及旧版 .zip.001 等字节分片。
2. 队列开始前弹窗确认替换，用户确认全部替换后才开始
3. 文件收集、复制和内容修改仍在任务临时目录中进行。mrpack包输出前先删除旧版目标文件，然后直接将最终 .mrpack 压缩到输出目录；完整包先在任务临时目录生成内嵌 modpack.mrpack，再删除旧目标。关闭分卷时直接输出外层 ZIP；启用分卷时在输出目录的独立临时目录内生成完整 ZIP 和分卷，完成转换后发布文件组。

删除前再次比较目标文件组、大小与修改时间；预检后出现新目标或已有目标变化时，不删除它们，要求重新预检及确认。启动实例使用工作目录数据区的 QLockFile 防止同一工作目录重复运行。损坏的工具设置不会自动覆盖；GUI 的修复操作先备份原文件，再恢复默认设置。

### 7.3 失败与取消清理

- 失败或取消时，先停止后台作业，再删除本任务已生成的未完成压缩包和临时目录

## 8. 实现组织与顺序

按以下职责拆分，核心导出流程可脱离 GUI 调用：

| 部分       | 职责                                                        |
| ---------- | ----------------------------------------------------------- |
| 配置与状态 | 发现任务、读取 TOML、解析路径、合并设置、保存勾选与窗口状态 |
| 实例识别   | 读取版本 JSON，生成 mrpack 依赖                             |
| 文件规划   | 匹配游戏规则、展开 extras 与自动 PCL 内容、检测目标冲突     |
| 复制与组包 | 建立任务临时目录、复制文件、生成索引和打包清单              |
| 压缩适配   | 调用 7za 压缩、Info-ZIP 转换原生分卷，解析阶段进度          |
| 覆盖与清理 | 确认覆盖、删除旧文件、直接输出成品、清理失败或取消的产物    |
| GUI 与调度 | 配置选择、预检展示、串行任务队列、进度与设置界面            |

实现顺序：

1. 验证 Windows 压缩/分卷工具链，固定构建来源、版本与依赖。
2. 完成配置读取、实例识别、文件规划及单任务mrpack包导出。
3. 完成完整包、原生 ZIP 分卷、覆盖确认和失败清理（已实现）。
4. 接入 GUI、批量调度、进度、取消、重试和状态记忆。
5. 使用真实实例做安装、兼容性、覆盖、取消和性能验收

## 9. 打包EXE

项目根目录已提供 `build_exe.bat`，通过 uv 的 build 依赖组调用 PyInstaller，生成携带 7za、Info-ZIP 及两套许可文件的单文件 Windows EXE。构建包含源码包内的 `vendor/` 和 `assets/`（含示例配置模板），不从 `docs/` 添加任何运行时文件；wheel 同样只从源码包收集运行时资源。`uv.lock` 固定依赖版本。
